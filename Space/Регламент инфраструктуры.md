# Регламент инфраструктуры (пользователь ⇄ Claude Code)

Канон инфраструктуры: имена хостов/дисков/сервисов, схема бэкапов, процедуры. Дополняет «Регламент взаимодействия» (архитектура источников правды). Живой документ: изменения — по проверенным фактам, с датой.

## 1. Что это и когда применяется

**Триггеры «инфраструктурной задачи»** (при любом совпадении — выполнить раздел 2):
сервер/хост/ВМ, бэкап, диск/шара/SMB/CIFS, mount/fstab, Zabbix/мониторинг/алерты, сеть/VPN/туннель, гипервизор (Hyper-V/ESXi), nginx/systemd-юниты на проде, диагностика доступности, любой из IP/имён из карты ниже.

## 2. Актуализация при инфраструктурной задаче (процедура)

1. **Прочитать** разделы 3 (Карта) и 5 (Регламент бэкапирования) **до начала работы** — не полагаться на память.
2. **Сверить факты с реальностью** командами (mount, crontab, статус-файлы, логи) — «диагностика вместо гаданий».
3. **Расхождения с картой/регламентом** → исправить регламент (пометка датой) и, если факт durable, — кратко в auto-память. Регламент — источник правды, память — производная.
4. **Сущность, которой нет в карте** → пометить «требует уточнения» (не выдумывать имена), при возможности проверить или спросить пользователя.
5. **Имена в отчётах — по канону раздела 3.4.** Отчёты заканчивать проверяемыми фактами (коды, выводы команд), непроверенное помечать.

## 5. Регламент бэкапирования

### 5.1 Политика

- Расписание: ежедневно **01:00** (cron: .178 — root, .128 — sa, .101/.108 — root).
- Каждый сервис — свой скрипт на своей машине: дамп/архив → локальная стадия → **параллельная запись на оба диска (132 и 72)** → проверка (md5/gzip -t/размер) → удаление стадии.
- **Retention 7 дней — только на дисках.** Локальная стадия (staging) — **без TTL**: хранит слепок, пока запись на диск не подтверждена; неподтверждённое не удалять (страховка).
- Режимы записи: **единая модель «стадия + копии» у всех четырёх** (fh/mm с 01.09, SUP и GitLab с 10.09): артефакт лежит в локальной стадии, пока не подтверждён на **обоих** дисках (сверка размера; у SUP/fh/mm — `gzip -t`, у GitLab — md5 тарника на одном диске), при недоступном диске день не теряется — стадия ждёт, её догоняет следующий прогон/сторож, статус FAIL → алерт; лимит стадии (`STAGE_MAX_MB` / `STAGE_MAX_GB`) защищает локальный `/` от ENOSPC. У SUP и GitLab пока есть неразложенное — новый снимок не создаётся (не копим на `/`); у GitLab для ручного догона есть `--flush-only`.
- Статус: статус-файл + Zabbix-метрики (раздел 4); **сторожевик у всех четырёх** (10.09): `backup_watch.sh` на SUP/fh/mm, `backup_watch_gitlab.sh` на .178 (cron root), период */30, условие «нет OK или успех старше 26 ч»; от задвоения защищает flock в скриптах бэкапа.

### 5.5 Действия при сбое ночного прогона

1. Прочитать статус-файл и хвосты логов на обоих дисках (у GitLab полный лог — `/mnt/windows_backup/Logs/backup_<TS>.log`, не `backup_cron.log`).
2. Определить фазу: создание → копирование → проверка. Проверить монтажи (`mount | grep cifs`), диск жив ли (замер записи ~1 ГБ, RTT).
3. Диск жив, но cp/копия FAIL → сверить фактический файл на диске (размер/md5): бывает «файл цел, cp упал в конце» (см. 5.4) — тогда копия засчитана, только поправить лейбл.
4. Канал узкий (.178) — длинные передачи могут обрываться: retry вручную копии `cp` и md5-сверка.
5. Если staging копит (диски лежат 2+ ночи) — `/` может заполниться (у .178 лимит check_space 25 ГБ); алерт Zabbix FAIL/STALE уже должен был прийти; почтовые письма проверять в action log при «метрики ушли, письма нет».
6. После восстановления — догнать пропущенные дни вручную и зафиксировать в разделе «грабли», если причина новая.

## 6. Регламент разработки

(вложен 09.09.2026 из «Регламент разработки.md» — правила процесса разработки для проектов в `Projects_Claude`; живой документ, дополняется по договорённостям. Связка: «Регламент взаимодействия» — архитектура источников правды, «Регламент инфраструктуры» — карта и бэкапы, этот раздел — правила кодирования и процесса.)

### Триггеры задач

- **«Фикс: …»** — делаем сразу: реализация + проверка + коммит в git с описанием.
- **«Бэклог: …»** — сейчас НЕ делаем: записываем задачу в `BACKLOG.md` (статус «открыто») + коммит. Вернёмся по команде «сделай B-XX».
- Прямое пожелание без ключевого слова («я хочу…») — уточняем трактовку, делаем сейчас.

### Git

- Репозиторий — в корне проекта (ветка main), история осмысленная (этапные коммиты, не «всё сразу»).
- Каждый фикс/бэклог-запись/правило — отдельный коммит с внятным сообщением.
- Секреты — в `.gitignore` (выгрузки с паролями, `.env` и т.п.) и никогда в истории.
- Сессия заканчивается коммитом незакоммиченных изменений.

### Проверка изменений на конфликты (обязательно перед каждым коммитом)

1. **Бизнес-логика**: изменение не противоречит согласованным решениям проекта:
   - справочники (категории/статусы) — данные БД, правятся в UI без миграций;
   - «удаление» = деактивация, история никогда не теряется;
   - инвентарный номер присваивается при создании и не меняется;
   - статусные переходы оборудования (склад → выдано → ремонт → склад/списано) не нарушаются.
2. **Логика**: не ломаются смежные сценарии (навигация-цепочка, фильтры/сортировка, заявки ↔ ремонт, актуализация, отчёты).
3. **Данные**: миграции применяются к существующим БД, импорт идемпотентен, новые поля не ломают старые записи.
4. **Техпроверка**: `npx tsc --noEmit` для фронта (без пересборки `.next` работающего dev), импорт приложения бэкенда, страница 200, логи `dev-logs/` без ошибок.
5. Если конфликт найден — остановиться и обсудить с заказчиком, а не «протаскивать» молча.

### Разработка и окружение

- Сервисы — фоновый демон (`scripts/dev-daemon.sh`), логи в `dev-logs/`; пользователь ничего не запускает, только обновляет страницу.
- Бэкенд — `uvicorn --reload`, фронт — `next dev` HMR: изменения применяются сразу.
- После каждой правки сообщать «готово, обнови страницу» + что изменилось.

### UI-соглашения

- **Esc управляет только отображением**: закрывает модалку → дропдаун фильтра → сбрасывает фильтры/сортировку экрана. Действия Esc НЕ откатывает.
- Фильтры и сортировка — в шапках таблиц (воронка у столбца, клик по заголовку — сортировка); активный фильтр подсвечивает столбец, метка `esc` — у активного столбца.
- Навигация-цепочка: любая сущность (номер, название, категория, ФИО) кликабельна и ведёт к карточке; из карточки можно идти дальше.

### Документация

- `README.md` (для новых разработчиков/РП) и `CLAUDE.md` (живой контекст) обновляются **параллельно** с изменениями/коммитами.
- Изменения правил вносить в этот регламент (+ в CLAUDE.md проекта при необходимости).

### Бэклог

- `BACKLOG.md` в корне проекта: ID / замечание / приоритет / статус. Проверять в начале каждой сессии.
